## 1. 阶段总览

PaperPilot 按接近商业产品的流程推进，而不是直接进入编码。整体过程分为八个阶段：

| 阶段 | 产出 | 说明 |
| --- | --- | --- |
| 1. 立项与问题定义 | 项目目标、范围边界 | 明确论文写作辅助系统的课程目标与产品方向 |
| 2. 市场与竞品调研 | 市场分析、国内外竞品调研 | 判断是否存在差异化机会 |
| 3. 用户研究 | 用户画像、痛点拆解 | 识别本科生、研究生、在职学生的不同需求 |
| 4. PRD 与商业分析 | PRD、MoSCoW、商业化路线 | 将需求转为可开发范围 |
| 5. 视觉稿与交互设计 | 页面截图、UI/UX 审计、体验优化计划 | 从工具式页面演进为成熟写作工作台 |
| 6. 技术方案与架构 | 前端架构、数据模型、API 方案 | 确认纯前端、BYOK、本地存储和 GitHub Pages 部署 |

| 8. 上线与发布 | GitHub Release、Pages workflow、线上验证 | 合并到 main 并完成线上发布 |

## 2. 立项与问题定义

### 2.1 初始目标

项目起点是构建一个论文写作辅助系统，用 AI 帮助学生完成选题、大纲、写作、文献和进度管理等任务。最初目标并不是做一个简单 Demo，而是尽量接近真实产品开发流程。

### 2.2 范围边界

经过早期讨论后确定边界：

- 做论文写作辅助，不做整篇论文代写。
- 使用用户自己的 API Key，避免后端成本和隐私风险。
- 保持纯前端架构，方便 GitHub Pages 部署。
- 本地保存数据，提供备份导出和导入。
- 以课程作业和内测体验为第一阶段目标。

## 3. 市场与竞品调研

### 3.1 调研对象

调研覆盖三类产品：

- 通用 AI 工具：ChatGPT、DeepSeek、豆包等。
- 国内论文写作产品：秘塔写作猫、火龙果写作、千笔论文等。
- 国际学术工具：Paperpal、Grammarly、Elicit、Consensus、Zotero 等。

### 3.2 调研结论

主要结论：

- 通用 AI 生成能力强，但缺少论文流程结构、引用和格式约束。
- 论文工具常见问题是功能单点化、付费强、合规信任不足。
- 文献管理工具专业但重，不适合非专业用户快速完成论文写作闭环。
- 论文计划管理是明显空白，适合作为 PaperPilot 的差异化记忆点。
- 国标引用、研究设计、写作台和计划管理的结合具有产品机会。

## 4. 用户研究

### 4.1 用户画像

项目提炼出三类典型用户：

| 用户 | 场景 | 关键问题 |
| --- | --- | --- |
| 本科应届学生 | 毕业论文、开题、格式整理 | 不会定题，不会搭大纲，格式容易错 |
| 在职研究生 | 工作与论文并行 | 时间碎片化，拖延严重，缺少推进计划 |
| 研究生用户 | 学位论文、投稿、综述 | 文献多，引用管理难，合规压力高 |

### 4.2 用户需求转化

用户研究将功能从“AI 生成文本”扩展为“论文项目管理”：

- 研究设计帮助用户少输入、多选择。
- 写作台承载连续论文正文，而不是多个孤立表单。
- 文献库需要和正文引用同步。
- 截止日期、打卡和计划是辅助项，不能阻塞写作主流程。
- AI 返回慢、失败、结构异常时必须给明确反馈。

## 5. 商业分析

### 5.1 产品定位

PaperPilot 的定位是：

> 覆盖论文全流程、内置写作计划管理、支持国标引用合规的轻量论文写作助手。

### 5.2 差异化能力

- 全流程：选题、研究设计、写作、文献、计划、导出。
- 合规：不做整篇代写，保留学术诚信提示。
- 低门槛：用户自带 Key，本地保存，无需账号。
- 中文论文友好：GB/T 7714、学位论文模板、Word/PDF/Markdown 导出。

### 5.3 商业化判断

当前架构适合 Beta 内测和课程展示。后续若商业化，需要新增：

- 账号系统。
- 云同步。
- 托管 AI 额度。
- 学校或导师协作。
- 合规说明与审阅报告。

## 6. PRD 形成过程

PRD 经历多轮演进：

- v1.0：初步构思，定义四大基础模块。
- v2.0：结合调研结果重写需求。
- v2.1：增加论文项目主线，解决模块割裂。
- v2.2：引入写作工作台。
- v2.3：把写作模型改为编辑器优先。
- v2.4-v2.10：加入章节初稿、真实文献检索、批量推荐、完整论文文档、国标引用和 UX 优化。

最终 PRD 采用 MoSCoW 方法划分优先级：

- Must：研究设计、写作辅助、文献检索、引用整理、计划、设置、项目主线。
- Should：文献库管理、导出、提示词模板。
- Could：更完整的 Word/PDF 样式、统计分析。
- Won't：整篇代写、AIGC 检测、账号云同步。

## 7. 视觉稿与交互设计过程

### 7.1 初始问题

早期界面存在：

- 卡片大小不一，留白不均。
- 功能一次性全部展开，流程不清晰。
- 写作区太窄，工具按钮拥挤。
- 研究设计页选项和生成按钮混在一起。
- 文献页和证据卡左右布局过重。
- 计划页指标和任务卡显得杂乱。

### 7.2 设计方向

最终采用“纸墨朱砂”视觉系统：

- 纸色背景。
- 墨色正文。
- 朱砂作为 AI、批注、警示语义。
- 松烟绿作为完成态。
- 写作区模拟论文稿纸。

### 7.3 关键交互改造

- 左侧全局导航可折叠。
- 写作台左侧论文目录可折叠和定位。
- 研究设计改为问卷流，用户直接选择即可推进。
- 最后确认方案时再提交进入大纲。
- AI 生成初稿直接进入正文编辑器。
- AI 修改工具以 diff/建议形式呈现，采纳后回写原位置。
- 文献库以列表为主，新增通过弹窗完成。
- 导出合并为 Word、PDF、Markdown 菜单。

## 8. 技术方案过程

### 8.1 架构选择

项目选择纯前端架构，原因是：

- 课程展示部署简单。
- 不需要维护后端服务。
- API Key 和论文数据可保存在用户本地。
- GitHub Pages 可免费托管。

### 8.2 技术栈

- Vite：开发和生产构建。
- JavaScript ES Modules：模块化业务代码。
- ProseMirror：富文本编辑器。
- localStorage / IndexedDB：本地数据持久化。
- OpenAI compatible API：适配 DeepSeek 等模型。
- GitHub Actions + GitHub Pages：上线发布。

### 8.3 重要技术决策

- 使用结构化文档模型，而不是普通 textarea。
- 文中只插入 `[n]`，完整参考文献在导出时自动生成。
- 真实 API 和本地模拟模式统一封装，避免流程未验证时消耗 Key。
- Word/PDF/Markdown 导出集中在写作台。
- GitHub Pages 使用 `dist/` 构建产物，不发布源码根目录。

## 9. 开发迭代过程

项目开发经历了多轮用户反馈驱动的迭代：

1. 搭建项目骨架和基础模块。
2. 引入论文项目主线，解决模块割裂。
3. 重构写作工作台，让编辑器成为中心。
4. 增加文献检索、批量推荐、证据卡和引用同步。
5. 重构研究设计，改为更像问卷的流程。
6. 优化首页、文献页、计划页和写作台 UI。
7. 增加富文本、图片、表格、公式、注释、版本管理。
8. 打磨 Word/PDF 模板预览和导出格式。
9. 发布 Beta 并修复 GitHub Pages 部署问题。

## 10. 测试方案

### 10.1 测试目标

- 核心流程可闭环。
- AI 慢响应和失败有反馈。
- 文献引用与文献库同步。
- 导出文件格式可用。
- 主要页面无明显 UI 错乱。
- 线上部署资源加载正确。

### 10.2 测试类型

| 类型 | 内容 |
| --- | --- |
| 构建测试 | `npm run build` |
| 功能走查 | 创建项目、研究设计、写作、文献、导出 |
| API 测试 | 本地模拟模式、真实 API、慢响应、失败提示 |
| UI 测试 | 桌面宽度、移动端 390px、卡片间距、按钮截断 |
| 导出测试 | Word、PDF、Markdown 人工打开检查 |
| 发布测试 | GitHub Actions 成功、首页/CSS/JS HTTP 200 |

## 11. 上线方案

### 11.1 发布流程

1. 修改版本为 `4.0.0-beta.1`。
2. 更新 README、release checklist 和 release notes。
3. 本地运行 `npm run build`。
4. 推送发布分支。
5. 创建 GitHub prerelease。
6. 创建 PR 合并到 `main`。
7. GitHub Actions 构建 `dist/`。
8. GitHub Pages 发布线上版本。
9. 检查线上首页、CSS、JS。

### 11.2 发布问题与修复

上线后发现页面无样式。排查结果：

- Vite 默认资源路径为 `/assets/...`，GitHub Pages 项目页部署在 `/paper-pilot/` 子路径，导致资源路径错误。
- 仓库中旧 workflow 将源码根目录发布到 Pages，覆盖了正确的 `dist/`。

修复：

- 新增 `vite.config.js`，配置 `base: './'`。
- 删除旧 `.github/workflows/static.yml`。
- 保留 `.github/workflows/pages.yml`，仅发布 Vite 构建产物。

## 13. 复盘结论

PaperPilot 的开发过程完成了从产品定义到线上发布的标准闭环。最大变化是：项目从早期的“多个 AI 功能页面”逐渐演进为“以论文项目和写作台为中心的连续工作流”。这使系统不只是能生成内容，而是能帮助用户在论文写作过程中持续推进、管理文献和输出可提交文档。

后续进入真实用户试用后，应重点收集三类反馈：

- 新用户是否能独立走完首次闭环。
- 真实 API 与文献检索是否稳定。
- Word/PDF 导出是否满足不同学校模板要求。
