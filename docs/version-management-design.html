01背景与问题

现状

写作工作台以「一份完整论文文档」为核心：题目 / 摘要 / 关键词 / 各章 / 参考文献 / 致谢拼装在单个编辑器中（buildDocument → parseDocument），编辑时 防抖 400ms 自动保存 到 paperpilot:drafts（按章节存 {content, updatedAt}），另有 Ctrl+S 强制保存与关页兜底保存。

现有的「撤销 / 重做」走 浏览器原生撤销栈（AI 动作经 execCommand('insertText') 进入原生栈，按钮走 execCommand('undo'/'redo')）。

问题

用户场景现状后果
AI「整章替换初稿」不满意，想退回生成前的版本原生撤销栈在 刷新 / 切换模块 / 隔天 后即失效；防抖自动保存又不断覆盖 drafts —— 一旦离开会话，任何改动都永久不可回退
手滑误删整段、误改标题行，过一会儿才发觉
隔天想找回昨天某个版本的写法 / 删掉的内容

结论：原生撤销栈解决「会话内、分钟级」的微操作回退；跨会话、天级的结构级回退需要独立的版本管理能力——这正是本设计要补的缺口。

约束前提（决定方案形态）

  • 无后端：版本数据只能落浏览器 localStorage（约 5MB 总量，写满抛 QuotaExceededError）
  • BYOK 合规：版本内容为论文草稿，不含 API Key（Key 只在 config 中）；版本随「设置→导出备份」一并导出，已有「含 Key 勿外传」警示
  • 结构保护教训（R10）：章节标题行是解析锚点，任何写回操作不得破坏「标题行 + 正文」的结构约束

02设计目标

编号目标说明
G1可回退任意章节可回到最近 N 天内的历史快照，恢复粒度到章节级
G2可反悔「恢复版本」本身可反悔：恢复前自动存档当前内容，恢复后仍可 Ctrl+Z
G3容量可控版本总量 ≤ 1.2MB 硬上限，只淘汰最旧自动快照，绝不挤占草稿 / 文献数据
G4零打扰自动快照无感（节流判定，不打断写作）；手动留档一键可达
G5隐私不变版本仅存本机 localStorage；不含 Key；随备份导出时遵循既有警示

03方案总览

三层结构，各司其职：

层回答的问题设计要点
捕获何时存一个版本？自动（10 分钟节流 + 500 字变化量 + Ctrl+S）+ 手动（「存为版本」按钮）+ 里程碑（章节完成）
存储存什么、存多少？按章节版本链（每章 ≤ 10 条）+ 整文档里程碑（≤ 5 条）；总量 1.2MB 双级淘汰
恢复怎么安全回到过去？只读预览 → 恢复前自动存档 → 章节正文替换（保留标题行）→ 进原生撤销栈 → 章节不存在时降级为素材库条目
核心取舍：按章节存版本，而非整文档 论文写作的「回退」几乎总是「退回某章某版」；章节级版本体积小一个数量级（单章 3KB–18KB vs 整文 30–100KB），同样的容量预算可多保留 5–10 倍的历史。整文档只保留少量里程碑版本（标记完成、Ctrl+S 时刻），覆盖「全文快照」诉求。

04详细设计

4.1数据模型

新增存储键 paperpilot:versions，与 drafts / project 并列：

paperpilot:versions = {
  chapters: {                              // 章节版本链，key = 章节名（与 drafts / outline 同键）
    "第一章 绪论": [
      { id: "m3k2q9", at: 1755..., src: "auto",     label: "",   text: "…正文（不含标题行）…" },
      { id: "m3k1f0", at: 1755..., src: "manual",   label: "定稿前版本", text: "…" },
      { id: "m3j0x7", at: 1755..., src: "milestone",label: "本章完成",  text: "…" },
    ],                                       // 最新在前；每章 ≤ 10 条
    "第二章 …": [ … ]
  },
  doc: [ … ]                                // 整文档里程碑（标记完成 / Ctrl+S），≤ 5 条
}
字段取值说明
idbase36(时间戳+随机后缀)唯一；排序与定位用
at毫秒时间戳展示用本地时间；也可用于节流判定
srcauto · manual · milestone来源徽标；淘汰时优先保 manual / milestone
label字符串（可空）手动留档时的用户备注；「恢复前自动存档」固定注记
text章节正文与 drafts[章节].content 同口径（不含标题行），恢复时与 chapterBodyRange 替换区间严格对齐

版本数据不含 config（API Key）与文献库，仅论文文档内容。

4.2捕获策略（何时存）

快照判定挂在 persistDocument（防抖落盘）之后执行，三个触发源：

来源触发条件示例场景
auto距上一快照 ≥ 10 分钟 且 正文有变化（逐字比较）连续写作每隔一段留一档
auto距上一快照 < 10 分钟，但本次变化 ≥ 500 字AI 整章替换初稿、整段粘贴——立即留档，不等节流
manual用户点工具栏「存为版本」（可填备注）重要节点主动留档
milestone① 标记章节完成；② Ctrl+S 保存且内容有变化；③ 切换章节时内容有变化且距上一快照 ≥ 1 分钟「本章完成」时刻、用户主动保存时刻自动留档
节流与兜底「10 分钟 + 500 字」双条件覆盖两种极端：长时间连续小改（节流防碎片）与大段一次性写入（变化量兜底立即留档）。Ctrl+S 是用户「此刻值得保存」的显式信号，无条件触发快照判定——这是两小时连续打字场景的第三重保险。

写入时机：快照写入发生在 防抖落盘之后，与 set(DRAFT_KEY, …) 同批次，不额外加锁；单次写入为整键覆盖（localStorage.setItem 原子），无并发风险。

4.3保留与容量（存多少）

双级淘汰，优先保 manual / milestone：

级别规则
每章上限每章 ≤ 10 条；超出删该章最旧 auto（若无 auto 则删最旧 manual）
整文档doc ≤ 5 条；超出删最旧
总量上限versions 序列化后 ≥ 1.2MB → 从最旧章节的最旧 auto 起淘汰，直至 < 900KB（每笔写入后检查一次，量小不阻塞）

容量预算（实测口径：中文 UTF-16 JSON，1 字 ≈ 3 字节含转义开销）：

场景单份版本满配占用结论
课程论文（单章约 1–2 千字）约 3–6 KB8 章 × 10 份 × 4.5KB ≈ 360KB ＋ 里程碑 5×30KB ≈ 150KB从容，远低于上限
学位论文（单章 4–6 千字）约 12–18 KB8 章 × 10 份 × 15KB ≈ 1.2MB触发总量淘汰 → 最旧 auto 渐次让位，manual 保底；此时草稿本身也接近 5MB 红线，属合理降级

淘汰只删 auto 旧档，永不触碰 drafts / project / citations——版本管理是「额外冗余」，没有它主数据也应完整。

4.4恢复语义（怎么回）

恢复是唯一有破坏性的操作，设计为四步、每步可反悔：

① 存档当前：先把编辑器当前全文按当前章节存一份 manual（label「恢复前自动存档」）→ 恢复后可一键回到「恢复前」
② 写入目标版本：findChapterRange 定位章节 → chapterBodyRange 得正文替换区间（保留标题行，复用现有防丢章机制）→ applyEdit 走 execCommand('insertText') 进入原生撤销栈（Ctrl+Z 可撤回本次恢复）
③ 自动落盘：applyEdit 派发 input 事件 → 既有防抖保存链路生效，drafts / 章节结构 / 摘要同步更新
④ 反馈：toast「已恢复到 08-20 14:32 的版本（Ctrl+Z 可退回）」；刷新字数 / 右栏引用计数
边界情形处理
目标章节仍在当前大纲正常恢复（上流程）
章节已被重命名 / 移出大纲（大纲结构保护，R10）该章版本归入「其他存档」分组：可预览、可删除；恢复仅支持「转存为素材库条目」（不破坏现有结构）
版本内容与当前完全相同toast「该版本与当前内容一致」，不落恢复前存档、不写编辑器
恢复时正在 AI 请求中请求结果写回前校验（既有 ta.isConnected 兜底），恢复流程照常执行

4.5界面设计

入口：工具栏「撤销 / 重做」右侧新增两个按钮——＋ 存为版本（次要）与 ⏱ 历史版本（主要）。点击「历史版本」打开右侧抽屉：

版本历史 ✕

  • 列表：按章节 tab 分组，最新在前；每条显示时间 · 来源徽标 · 字数 · 备注
  • 预览：抽屉内只读展示该版本正文（头部注「章节 · 时间 · 字数」），不打断编辑器
  • 恢复：弹确认「将用 08-20 21:40 的版本覆盖本章当前内容（当前内容会自动存档）」
  • 容量条：抽屉底部实时显示占用与上限，快触顶时变朱砂色提示「可到设置页导出备份」
  • 首版不做逐字 diff（版本间「对比当前」高亮成本高、收益低），以字数差 + 内容预览替代，diff 列为二期

05与现有机制的分层关系

三种「回退」机制互补，不重叠、不打架：

机制粒度时效失效条件典型用途
原生撤销栈
（现有）		单次编辑会话内刷新 / 切换模块AI 动作不满意，Ctrl+Z 即时撤回
版本管理（新增）章节 / 文档级快照跨会话持久手动清除本地数据「昨天那版」找回、AI 整章替换后悔药、误删恢复
备份导出
（现有）		全量 JSON 文件文件级文件丢失换机 / 清缓存迁移、灾备

版本管理实现后，原生撤销栈与备份导出均保持原样——三者的差异是粒度与时效，不是替代关系。

06验收与测试

Playwright 回归（新增断言）

#场景断言
V1存为版本 → 修改章节 → 恢复该版本编辑器章节正文回到旧文本；恢复前存档存在（可再恢复回去）
V2恢复后立即 Ctrl+Z回到恢复前的状态（恢复进原生撤销栈）
V3只改 1 个字（10 分钟内）不产生新版本（节流生效）
V4AI 整章替换（变化 > 500 字）立即产生新 auto 版本
V5Ctrl+S内容有变化时产生 milestone 版本
V6构造 11 个版本每章列表长度 = 10（最旧 auto 被淘汰，manual 保留）
V7注入大文本逼近 1.2MB触发总量淘汰，最旧 auto 消失；drafts 不受影响
V8章节重命名后查看旧版本旧版本出现在「其他存档」，恢复仅提供「转素材库」

真机自测（用户侧）

  • 写一章 → 点「存为版本」→ 大幅改写 → 从历史版本恢复 → 内容回到旧版，且 Ctrl+Z 可退回
  • 隔天打开（浏览器重启后）→ 历史版本仍在 → 可找回昨天的版本
  • 设置页导出备份 → 清除数据 → 导入备份 → 版本历史完整

07风险与取舍

风险 / 取舍应对
localStorage 总量 5MB，版本会挤占草稿空间1.2MB 硬上限 + 双级淘汰；淘汰绝不触碰主数据；容量条实时可见，触顶引导导出备份
自动快照可能过密（碎片）或过疏（漏档）「10 分钟节流 + 500 字变化量 + Ctrl+S」三触发互补；节流判定逐字比较，无 hash 依赖
章节重命名后旧版本找不到归属「其他存档」分组：可预览 / 删除 / 转素材库，不破坏大纲结构（R10 同源教训）
恢复操作覆盖当前内容恢复前自动存档 + 进原生撤销栈，双重可反悔
逐字 diff 成本高首版不做 diff，以字数差 + 内容预览替代；diff 高亮列二期（如需）
性能快照写入与防抖落盘同批次（400ms 防抖已自然合批）；逐字比较 O(n) 微秒级；evict 量小同步执行
合规红线对齐版本能力不改变 BYOK 边界：Key 仍只存 config 且不进版本内容；版本随备份导出时沿用「含 Key 请勿外传」警示文案；本能力不集成任何 AIGC 检测、不改变「不代写整篇论文」的产品红线（版本只是记录与回退，不新增生成能力）。
